CONFIRMED UART ROOT CAUSE
=========================

Stage 4D3 Linux diagnostics identify the Super I/O as a Winbond-family
device at configuration ports 0x2E/0x2F:

  device ID 0xB0, revision 0x73
  probable W83627DHG-P/-PT family

Its logical devices are configured as:

  LDN 02 COM1: active, base 0x3F8, IRQ 4
  LDN 03 COM2: active, base 0x2F8, IRQ 3
  LDN 0B hardware monitor: inactive, base 0x0000

The Intel H61 LPC controller initially reports:

  LPC_IO_DEC 0x80 = 0x0000
  LPC_EN     0x82 = 0x1400

LPC_IO_DEC selects the standard 0x3F8/0x2F8 COM ranges, but LPC_EN bits
0 and 1 (COMA_EN and COMB_EN) are clear. All UART I/O reads consequently
return 0xFF and Linux reports uart:unknown.

The following runtime test was hardware successful:

  setpci -s 00:1f.0 82.w=0003:0003

Afterward LPC_EN reads 0x1403, COM1 registers become accessible, LSR is
0x60, setserial identifies a 16550A, and data reaches the physical serial
interface. Late reassignment of the already-running ttyS0 console can
produce garbled output; the decode must be enabled before kernel startup.

GRUB workaround:

  insmod setpci
  setpci -s 00:1f.0 82.w=0003:0003

Place these commands in the menuentry before the linux command. Use only
one serial kernel console:

  console=tty1 console=ttyS0,115200n8 \
  earlycon=uart8250,io,0x3f8,115200 ignore_loglevel

This workaround is reset on every power cycle and does not modify flash.
The permanent firmware fix is to set COMA_EN and COMB_EN before BDS/kernel
handoff.

Fan control remains a separate issue: Winbond hardware-monitor LDN 0B is
inactive and has no assigned base address.

Stage 2B comparison and Stage 4C runtime fan test:

  Stage 2B programs:

    LPC_IO_DEC 0x80 = 0x0010
    LPC_EN     0x82 = 0x3F07
    GEN1_DEC   0x84 = 0x000C0291
    Winbond LDN 0B  = active, base 0x290, F0=0x80, F2=0x80

  Its four Winbond PWM channels are in manual PWM mode with duty 0x0A.
  The enable_w83627_stage4c.sh runtime initializer reproduces the decode
  and HWM setup while using free ONDA GEN2_DEC instead of replacing its
  GEN1_DEC window.

  Hardware results on Stage 4C:

    full mode, PWM 0xFF:
      maximum fan speed/noise

    lanner mode, PWM 0x0A:
      fan remains rotating at a quiet low speed

BIOS SERIAL CONSOLE REDIRECTION ANALYSIS
========================================

The ONDA firmware already contains AMI Terminal and LEGACYSREDIR DXE
drivers. Its Advanced IFR contains a Serial Port Console Redirection
form and the following relevant settings in the Setup variable
EC87D643-EBA4-4BB5-A1E5-3F3E36B20DA9:

  Setup[0x295]  COM0 Console Redirection, default Enabled
  Setup[0x297]  COM0 terminal type, default ANSI
  Setup[0x289]  COM0 baud rate, default 115200
  Setup[0x28B]  COM0 data bits, default 8
  Setup[0x28D]  COM0 parity, default None
  Setup[0x28F]  COM0 stop bits, default 1
  Setup[0x291]  COM0 flow control, default None

COM0 visibility is conditional on byte 0 of the volatile two-byte
SerialPortsEnabledVar under GUID
560BF58A-1E0D-4D7E-953F-2980A261E031. The corresponding IFR question is
QuestionId 0x148. COM1 uses byte 1 and QuestionId 0x147.

The Stage 4F2 image has both serial devices enabled in NVRAM:

  PNP0501_0_NV = 01 00 00
  PNP0501_1_NV = 01 00 00
  SioSerialPortsLocationVar = 00 01 FF FF

However, the image's ConOut variable contains only the integrated
graphics device path, and ConIn contains graphics/keyboard paths. Neither
contains a UART node or a terminal-emulation vendor node. Enabling the
Setup default alone therefore cannot redirect pre-OS firmware output.

Preferred hardware experiment before building another image:

  1. Enter ONDA Setup and open Serial Port Console Redirection if visible.
  2. Set COM0 Console Redirection to Disabled, save, and reboot.
  3. Set it back to Enabled at 115200 8N1 with no flow control, save, and
     reboot.
  4. Check whether AMI's Setup callback creates the serial ConOut/ConIn
     device paths and firmware output appears on COM1.
  5. If successful, capture a fresh full flash dump before constructing
     a reproducible default patch.

Do not copy ConOut/ConIn blindly from another board. A future Stage 4F3
must either use the device paths generated by this exact ONDA SIO stack,
or locate the firmware Serial I/O handle and construct the matching
terminal child path dynamically.

REPRODUCIBLE RELEASE BUILD
==========================

The exact Stage 4GH release can be rebuilt from the external inputs pinned in
build-inputs.json:

  1. tools/build_lanner_me8_stage1.py reproduces the verified Stage 1 image
     from the original Lanner read, ASRock H61M-ITX 2.00, and Intel FITC
     8.1.40.1456.
  2. Stage 1 must be flashed and booted once. The resulting Intel ME runtime
     state and active NVRAM are captured in post-stage1-boot-readback.bin.
  3. tools/build_release.py --check-only validates every release input.
  4. tools/build_release.py executes the exact 22-step Stage 4C-to-4GH chain
     and requires the final published SHA-256.

The direct release-base builder reproduces hardware-tested Stage 4C SHA-256:

  8523a25786da11675e5de769e77dfe2347dfec818e6e83d4e4737068b79fb4b7

The historical x7-vb.bin donor is from the Angxun ANGTHUMB XLZ X7-VB V2.0:

  https://theretroweb.com/motherboards/s/angxun-angthumb-xlz-x7-vb-v2-0-h61

It contains embedded names X7VB1001.rom and X7VB1001. This particular BIOS
build identifies itself through SMBIOS as AISURIX H61 Motherboard V2.0,
consistent with a rebranded or later firmware identity. Its Stage 2A
microcode change is within 0x420000-0x57FFFF, which Stage 4C erases
completely. Angxun, ASUS, and all diagnostic Stage 2/3 experiments are
therefore not release-build inputs.
